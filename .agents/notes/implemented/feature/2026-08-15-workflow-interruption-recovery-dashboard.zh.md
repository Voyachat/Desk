# Agent Note：工作流恢复机制在显式重启前记录中断状态

[English](2026-08-15-workflow-interruption-recovery-dashboard.md) | 中文

状态：已实现

## 问题

工作流运行由 Session 事件持久化描述，但进程退出可能导致最后一条成员事件和运行事件处于未终止状态。将这段历史回放为 `running`，会错误地暗示一个已不存在的 worker 仍持有活跃工作。重启后自动重新提交工作流，还可能重复模型调用或工具副作用。既有的单消息卡片也无法提供当前 Session 内多个运行及其恢复状态的统一视图。

## 决策

父级 Session 的 `tool-workflow/*` 事件流仍是唯一的工作流恢复 owner。`tool-workflow/run-start` 记录发起运行的工具 `callId`。当 Session 以 `resume` 来源启动时，工作流插件扫描持久化历史，并为每个未终止成员和运行追加 `interrupted` 终止事件。重复恢复具备幂等性，且绝不会调用工作流引擎。

中断或失败的运行只能通过显式命令重试。该命令解析已记录的 `callId`，读取原始持久化 `tool/call` 参数，并在用户确认后从头创建一次新运行。它不声称支持检查点或步骤中途继续。

Client 保留既有对话卡片，并为当前加载的 Session 增加 `conversation.session.header.actions` 仪表盘。两个视图都把相同的持久化事件折叠为运行和步骤状态。该仪表盘不创建第二套 Host 状态存储，也不承诺跨 Session 聚合。

## 曾考虑的替代方案

重启后仍把未终止运行标为 `running` 的方案被否决，因为已经没有 worker 可以结算它们。自动回放未终止运行的方案被否决，因为工具调用未必具备幂等性。持久化独立仪表盘数据库的方案被否决，因为它可能与 Session 事件流发生偏离。宣称支持检查点恢复的方案被否决，因为工作流引擎不会持久化可执行的步骤检查点。

## 后果

崩溃或重启后，未完成工作会明确显示为已中断，并可在不自动重新执行的前提下恢复。显式重试会生成一次新的可审计运行，同时保留中断历史。当前 Session 仪表盘通过 Session 回放跨页面刷新保留状态，并展示多个运行和步骤；未来的跨 Session 仪表盘仍需要独立的 Host 查询能力。
