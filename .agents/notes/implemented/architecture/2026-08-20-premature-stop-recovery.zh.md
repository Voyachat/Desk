# Agent Note: 过早停止恢复

状态：已实现

[English](2026-08-20-premature-stop-recovery.md) | 中文

## 问题

提供方可能在生成一段宣布下一项立即动作的文本后返回 `stop`，却没有发出对应工具调用。默认 agent loop 会正确规范化该提供方响应，但不能把提供方意图等同于用户任务完成。将每个纯文本 `stop` 都记为 `turn/end: completed` 会让 UI 把 Turn 展示为已成功结算，即使承诺的动作没有运行。

## 决策

`@voyaseek-ai/dsh-premature-stop-recovery` 观察既有 `agent/turn-stopping` 扩展点。它只检查当前 Turn 中最后一个标准提供方结束原因和 assistant 消息，要求 `finish.kind: stop`，拒绝包含工具调用的消息，并匹配范围有界、无条件的中文或英文动作承诺尾句。匹配后，它把一条固定的插件来源消息 steering 到同一 Turn 的下一个 Step。每个 Agent 和 Turn 使用一个可配置的连续无进展上限；每个完成的 `tool/result` 都会重置该上限，因此有实际进展的多步任务没有总轮次上限。用尽无进展上限后会准入一个固定的未完成结果报告 Step，此后若再次匹配，则记录 warning 并关闭。

恢复消息是普通的持久 `user/message`，因此请求重建、持久化、回放、UI 历史和 Session 导出都会保留该决策，无需新增事件类型或诊断存储。`max-tokens`、错误、取消、没有标准结束原因证据的其他 driver、结果陈述和条件式提议均保持不变。

## 结果

复现中的中文尾句会自动继续，并保持一个 Turn 边界。产生工具结果后会重置无进展计数，因此反复中断不会终止仍在推进的任务。每次介入都能在 Session 日志中归因，同时持续不遵循要求的模型无法产生无限无进展循环。检测特意保持不完整：假阴性会保留提供方停止，而更宽泛的语义任务验证继续由 goal 策略负责。

## 备选方案

修改 `agent-loop`、将每个提供方 `stop` 都视为不确定被否决，因为普通文本完成是合法行为，而且已有文档化停止钩子支持数据驱动继续。新增第二套调试日志被否决，因为 Session 日志已经包含提供方结束原因、assistant 文本、恢复来源、后续工具和最终 Turn 原因。每次响应后都运行验证模型被否决，因为它会为正常对话增加延迟和成本，并与显式复杂 goal 验证重叠。
